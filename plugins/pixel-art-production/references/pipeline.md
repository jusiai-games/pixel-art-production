# 픽셀 아트 제작 절차

## 첫 요청 인터뷰

AI는 아트 방향 파일이 없거나 상태가 `초안`인 게임의 첫 이미지 요청에서 인터뷰를 시작한다. 요청과 기존 초안에 이미 적힌 답은 사용하고, 필요한 질문을 2~3개씩 묻는다.

1. 프로젝트 이름, 게임 콘셉트와 장르, 핵심 플레이를 묻는다. 첫 이미지가 캐릭터·타일·효과 중 무엇인지와 게임에서 어떻게 쓰이는지 확인한다.
2. 카메라 각도와 첫 에셋에 필요한 방향, 원하는 분위기와 피할 표현, 실루엣이나 캐릭터의 특징을 묻는다. 기본 플레이 배율에서 꼭 읽혀야 하는 요소를 확인한다. 레퍼런스가 있으면 이미지나 경로를 받고 어떤 요소를 참고할지 확인한다. 레퍼런스가 없으면 지금까지 들은 내용을 바탕으로 톤과 색 후보를 제시한다.
3. 들은 내용을 짧게 요약하고, 대표 장면에서 쓸 배경·캐릭터·위험·효과의 대비와 재질별 HEX 팔레트를 제안한다. 사용자가 방향을 정하면 설정을 저장하고 원래 요청한 첫 에셋을 이어서 제작한다. 대표 장면이나 전 방향 포즈가 아직 없으면 첫 이미지부터 기준 후보를 만든다.

### 캐릭터 프레임 선택

첫 인터뷰에서 화면 해상도와 캐릭터의 목표 높이를 확인한다. 프레임은 캐릭터와 동작 여백을 포함하는 캔버스다. 모든 캐릭터가 같은 프레임을 사용해도 화면에 보이는 높이는 서로 다를 수 있다.

| 프레임 | 발 피벗 | 선택 기준 |
| --- | --- | --- |
| 16×16 | (8, 14) | 작은 캐릭터와 단순한 실루엣 |
| 24×24 | (12, 21) | 작은 캐릭터에서 장비나 자세를 구분할 여유 |
| 32×32 | (16, 28) | 얼굴과 장비를 간략하게 읽히게 할 때 |
| 48×48 | (24, 42) | 높이 약 36px인 캐릭터와 동작 여백 |
| 64×64 | (32, 56) | 큰 캐릭터나 크게 펼쳐지는 자세 |

사용자가 고른 크기는 첫 에셋을 만들기 전에 저장한다. 예를 들어 `& $py $tool lock-character-frame $game 48`로 `character-frame.json`을 만든다. 이후 명령은 같은 프로젝트의 다른 크기 설정 요청을 거부한다. 모든 캐릭터 매니페스트는 이 파일을 공유한다. 크기 파일을 수동으로 바꾸지 않는다. 기존 설정 파일이 없는 작업은 호환성을 위해 32×32를 사용한다.

### 인터뷰 결과 저장

1. `project/game/`이 없으면 AI가 Python 3.10 이상과 플러그인 `scripts/pixel-art/requirements.txt`의 의존성을 설치하고 `init project/game`을 실행한다. 기존 폴더가 있으면 내용을 이어서 채운다. 프로젝트 이름은 `art-direction.md`에 기록한다.
2. `art-direction.md`에 콘셉트, 카메라, 톤, 조명, 대비, 역할별 색과 기본 배율에서 읽혀야 하는 요소를 기록한다. 첫 에셋에 필요한 방향을 합의하면 상태를 `확정`으로 표시한다. 화면에서의 크기와 배경 대비처럼 실제 플레이로 판단할 내용은 확인할 가정으로 남긴다.
3. 합의한 HEX로 `palettes/project.json`의 예시 색을 교체한다. 재질별 색 램프와 검사 가능한 조명·외곽선 기준은 `styles/default.json`에 기록한다. 역할별 색 제한이 필요하면 팔레트 파일을 추가하고 해당 매니페스트에 연결한다.
4. 첨부된 레퍼런스를 `references/`에 저장하고 출처와 참고할 요소를 기록한다. 팔레트 견본을 만든다. 첫 제작에서 승인한 포즈와 대표 장면은 이후 작업의 기준 레퍼런스로 추가한다.

원하는 색감이 담긴 PNG가 있으면 [PNG 레퍼런스 색감 선정](color-style.md)에서 참고할 영역과 재질별 그림자·기본색·하이라이트를 선택한다. 승인된 레퍼런스로 프로파일과 생성 가이드를 만든다.

```powershell
$tool = '<플러그인 루트>/scripts/pixel-art/pixel_art.py'
$game = 'project/game'
& $py $tool swatch "$game/palettes/project.json" "$game/references/palette-v1.png"
```

## 개발 중 아트 방향 갱신

`확정`은 첫 에셋 제작에 필요한 기준을 합의했다는 뜻이다. 첫 기준 포즈, 이동과 조준, 첫 전투 화면처럼 새로 확인할 수 있는 결과가 생기면 사용자와 함께 살펴보고, 다음 제작에 필요한 기준을 합의해 갱신한다. 초기 인터뷰에서 남긴 가정은 실제 화면에서 확인하는 시점에 결정과 근거를 기록한다.

여러 에셋에 적용할 기준은 `art-direction.md`에, 개별 동작의 방향이나 프레임 타이밍은 해당 작업 명세에 기록한다. 게임 전체의 톤·팔레트·광원이 바뀌면 [아트 방향 변경](#아트-방향-변경)에 따라 영향받는 에셋을 다시 검수한다.

## AI 이미지 생성과 편집

1. `jobs/_template.md`를 복사해 작업별로 채운다. 예를 들어 대기부터 만든 뒤 걷기나 공격으로 확장한다. 각 동작의 방향, 프레임 순서와 지속 시간(ms), 반복 여부, 접지 또는 발동 시점을 기록한다.
2. 새 포즈에는 승인한 같은 방향의 기준 이미지, 팔레트 견본과 실제 HEX를 첨부한다. 캐릭터는 `character-frame.json`의 크기와 위 표의 발 피벗을 작업 명세와 프롬프트에 넣는다. 색감 프로파일이 있으면 [캐릭터 생성에 적용](color-style.md#캐릭터-생성에-적용)하는 방법을 참고해 재질별 명암과 채도 목표를 적는다. 다음 문장을 작업 명세에 맞춰 바꿔 쓴다.

   > 첨부 기준 포즈에서 [동작과 방향] 한 프레임을 만든다. [카메라 각도]와 [실루엣·비율·비대칭 요소]를 유지하고 [바꿀 요소]만 바꾼다. 조명은 [방향], 재질별 허용 색은 [HEX]다. [프로젝트에 고정한 N×N] 논리 격자, 투명 배경, 불투명한 픽셀 경계. 기준 발 위치는 좌상단에서 [프로젝트 발 피벗]이다.

3. 생성 원본과 프롬프트를 `sources/<asset>/<attempt>/`에 보관한다. AI 후보에서 픽셀 블록이나 배경이 불규칙하면 픽셀 편집기로 프로젝트의 고정 격자와 투명도를 맞춘 뒤 내보낸다. 규칙 격자가 확인된 시트는 `split`으로 분리할 수 있다. 확대본은 블록이 정확히 일정할 때 `normalize --scale N`으로 축소한다.
4. 후보를 원본 크기, 최근접 4배 확대와 게임 장면에서 비교한다. 연속 프레임에서 발 기준점, 보폭, 표정, 손과 광원이 튀는지 확인하고 승인본을 `approved/<asset>/`에 둔다.

## 검수와 시트 조립

확대된 생성 원본은 축소하거나 색을 보정하기 전에 `inspect-grid`로 검사한다. 의도한 확대 배율을 `--scale`에 지정한다. 격자의 시작점이 캔버스 원점에서 어긋난 경우 `--origin X Y`에 한 칸 안에서의 오프셋을 지정한다. 배율이 추정치라면 보고서의 표시를 해당 가정에 따른 후보 위치로 읽는다. 배율이 알려진 32×32 후보의 예시는 다음과 같다.

```powershell
& $py $tool inspect-grid "$game/sources/hero_idle/01/generated.png" "$game/work/hero_idle-01/source-grid" --scale 32
```

`grid.png`의 분홍 테두리는 칸 내부의 색 또는 알파가 일정하지 않은 위치다. `report.json`에 해당 영역의 좌상단 원점 좌표, 부분 투명 픽셀 수와 캔버스 정렬 여부를 기록한다. 원본을 보정하더라도 이 결과를 보관한다.

예시는 `sources/hero_idle/01/hero_idle_down_00.png`에 32×32 후보가 있는 상태에서 실행한다. 각 출력 경로는 처음 쓰는 경로를 지정한다. 단일 PNG 후보는 `normalize`, 규칙 격자 시트는 `split`을 호출한다. AI는 팔레트와 스타일 설정을 읽고 `review`를 실행한 뒤 결과와 경고를 확인한다.

```powershell
$manifest = "$game/manifests/hero_idle.json"
$run = "$game/work/hero_idle-01"
$frame = 'hero_idle_down_00.png'
& $py $tool normalize "$game/sources/hero_idle/01/$frame" "$run/frames/$frame" --kind character
& $py $tool review $manifest "$game/styles/default.json" "$run/frames" "$run/review"
```

- 캐릭터의 얼굴을 확인할 때 `review`에 `--face-box X Y W H`를 추가한다. 좌상단에서 잰 얼굴 영역을 같은 실행의 모든 프레임에 적용한다. 예를 들어 `--face-box 16 9 8 7`은 1배 전체 프레임과 해당 영역의 8배 최근접 격자 확대를 `<frame>-face.png`에 저장한다. 방향이나 동작별 얼굴 위치에 맞춰 영역을 선택하고, 승인 전에 1배에서 눈과 입이 따로 읽히는지 확인한다.
- `review`는 `preview-01.png`, `report.json`, 보정 후보 `frames/`를 만든다. 기본 스타일은 팔레트와 프레임 규격을 검사한다. 재질별 보정이 필요하면 스타일 JSON에 `ramps`(어두운 색부터 밝은 색), `source_materials`(팔레트 밖 HEX → 재질 이름)를 명시한다. 대상 색은 매니페스트 팔레트 안에 있어야 한다. 재질이 불명확한 색은 이미지 편집기에서 확인한다.
- 캐릭터 색감 프로파일이 있으면 `review --color-profile <profile.json>`으로 보정 후보의 색감 편차를 기록한다. 시전 효과처럼 몸체 분석에서 제외할 전용색은 `--color-ignore '#HEX'`로 넘긴다.
- 선택적으로 `outline`의 `colors`, `replace`, `minimum_coverage`와 `light`의 `direction`(예: `upper_left`), `tolerance`, `ignore_colors`를 설정한다. 윤곽선과 광원 경고는 눈으로 확인한다.
- 시트 입력은 `split <manifest> <png> <out>`을 쓴다. `--scale`, `--margin`, `--gap`은 원본 격자에 맞춘다. 팔레트 보정을 검수 단계에서 할 때는 `--defer-palette`를 쓴다. 필요하면 분리 후 각 프레임을 정규화한다. 캐릭터 발 위치를 직접 읽었다면 `normalize --anchor X Y`로 맞춘다.

팔레트 검사에 실패하면 해당 색이 어느 재질에 쓰였는지 확인한다. 기존 색으로 맞출 수 있으면 재질 매핑이나 원본 후보를 수정한 뒤 검수를 다시 실행한다. 새 색이 디자인에 필요하면 사용자와 색을 정하고 [아트 방향 변경](#아트-방향-변경) 절차를 적용한다. 같은 후보 PNG와 검수 설정으로 검수·보정·조립을 반복할 수 있다.

단일 스프라이트는 승인한 프레임 PNG가 최종 산출물이다. 시트가 필요하면 미리보기를 승인한 뒤 다음처럼 조립한다. 조립 결과에서 PNG를 바로 사용할 수 있다.

```powershell
Copy-Item "$run/review/frames" "$game/approved/hero_idle"
& $py $tool assemble $manifest "$game/approved/hero_idle" "$game/exports/hero_idle-v1"
```

| 매니페스트 | 셀 / 피벗 | 배치 |
| --- | --- | --- |
| `character` | 프로젝트 고정 크기 / (크기의 ½, 크기의 ⅞) | `frames_per_direction`, `directions`는 down/left/right/up 순의 부분집합. 파일명은 `<name>_<direction>_<index:02>.png` |
| `tile32` | 32×32 / (16, 16) | `tiles` ID 배열과 `columns`. 파일명은 `<name>_<id>.png`. 중앙 피벗 소품·효과도 같은 규격 사용 가능 |
| `tile` | 16×16 / (8, 8) | 기존 소형 타일과 효과용. `tile32`와 같은 배열 |

피벗 표기는 좌상단 원점 픽셀 경계 좌표다. 모든 프로필은 32 PPU다. 캐릭터의 `columns`는 방향당 프레임 수의 약수로 지정하며 기본값은 방향당 프레임 수다. 팔레트 경로는 매니페스트 기준이다. CLI 옵션은 `--help`와 각 명령의 `--help`에서 볼 수 있다.

## UI 실루엣과 화면 배율 검수

1. 새 UI를 만들거나 수정하기 전에 첨부 레퍼런스에서 가져갈 형태를 한 줄로 기록한다. 예를 들어 양피지 이름표는 가운데 종이 띠가 곧고, 양끝에서 같은 종이가 뒤로 돌아가 안쪽 단면이 보인다. 배경이나 기존 UI의 장식이 겹칠 때도 이 형태가 읽혀야 한다.
2. 원본과 최종 스프라이트의 픽셀 격자를 확인한다. 해당 UI 빌드에서 알파·허용색·타일 재조립과 늘어나는 영역을 검사한다. 9슬라이스는 좁은 폭과 평상시 폭, 긴 텍스트 폭에서 고정 영역을 확인한다.
3. 기술 검사 후에는 이름표, 대화창, 실제 버튼이 함께 있는 화면을 1배와 같은 정수 확대 배율로 확인한다. 레퍼런스의 핵심 특징이 기본 표시 크기에서 읽히는지, 이름표가 버튼처럼 보이는지 확인하고 결과를 기록한다.

## 상태 전환 검수

캐릭터 애니메이션을 만들거나 수정할 때 먼저 게임에서 어떤 상태로 들어오고 어디로 나가는지 확인한다. 이미 합의한 전환, 작업 명세나 실제 재생 키에 있는 정보를 사용한다. 사용자 피드백이나 미리보기에서 어느 동작 사이인지, 피격이 어느 시점인지, 도착 클립이 어느 프레임에서 시작하는지 불분명하면 필요한 내용을 사용자에게 묻는다. 확인된 전환을 게임 폴더의 상태 전환 맵에 기록하고 이후 수정 시 함께 갱신한다.

맵의 각 연결에는 이름과 실제로 이어지는 두 개의 개별 PNG를 지정한다. 같은 상태라도 일반 종료와 중도 피격은 별도 연결이다. 여러 프레임에서 중단될 수 있으면 검사할 대표 시점을 각각 추가한다. 쓰러지는 중간처럼 큰 자세 변화가 검수 대상이면 동작 내부의 프레임 쌍도 등록할 수 있다.

예를 들어 게임 폴더에 `wizard-state-transitions.json`을 두고 다음처럼 작성한다. PNG와 팔레트 경로는 맵 파일을 기준으로 한다.

```json
{
  "palette": "palettes/wizard_shared.json",
  "effect_colors": ["#78CBF4", "#ADE9FF", "#F0FCFF"],
  "outline_colors": ["#201B2D", "#222034", "#28283F"],
  "limits": {
    "min_overlap": 0.4,
    "max_color_shift": 0.35,
    "min_outline_coverage": 0.7,
    "max_cluster_shift": 0.16,
    "max_contact_shift": 2
  },
  "edges": [
    {
      "id": "idle_to_cast",
      "from": "work/idle/review/frames/hero_idle_right_00.png",
      "to": "work/cast/review/frames/hero_cast_right_00.png",
      "mode": "exact"
    },
    {
      "id": "cast_peak_to_fall",
      "from": "work/cast/review/frames/hero_cast_right_06.png",
      "to": "work/fall/review/frames/hero_fall_right_02.png",
      "mode": "pose",
      "limits": { "min_overlap": 0.3 }
    }
  ]
}
```

개별 프레임의 `review`를 마치면 전환 검사를 실행한다. 수정한 동작이 맵의 다른 동작에도 연결되면 해당 연결까지 다시 검사한다.

```powershell
& $py $tool review-transitions "$game/wizard-state-transitions.json" "$game/work/wizard-transitions-01"
```

- 허용 색 위반과 `exact` 경계의 픽셀 불일치는 실패다. 색 위반과 정확 일치 실패는 결과를 기록한 뒤 종료 코드 1을 반환한다. 크기나 알파 규격에 맞지 않는 입력은 오류로 중단한다.
- 실루엣 겹침, 몸체 색 분포, 외곽선 커버리지, 같은 색 인접 픽셀 비율, 최하단 불투명 픽셀 높이는 지정한 기준을 벗어나면 경고다. 전용 이펙트 색은 몸체 통계에서 제외한다. 맵 전체의 기준을 연결별 `limits`로 조정할 수 있다.
- `report.json`과 연결별 4배 PNG를 확인한다. 차이 패널에서 주황은 색이 바뀐 픽셀, 분홍은 사라진 픽셀, 하늘색은 새 픽셀이다. 마지막 패널의 주황은 도착 프레임의 외곽에서 윤곽선 색이 아닌 위치다.
- 경고는 해당 자세에서 변화가 의도된 것인지 확인하는 데 쓴다. 픽셀 통계는 모자나 망토를 자동 식별하지 않으므로, 자세별 임계값은 기준 포즈와 문제가 있었던 이전 시트를 비교해 정하고 실제 배율에서 연결을 재생해 확인한다. 실패를 수정하고 경고를 검토한 뒤 시트를 승인한다.

## 아트 방향 변경

- **개별 에셋 수정**은 해당 작업 명세와 마지막 승인 PNG를 기준으로 시작한다. 게임 전체 설정을 유지하고 새 후보를 별도 시도로 저장한다. 사용자가 수정 결과를 채택하면 작업 명세와 최종 PNG 경로를 갱신한다.
- **게임 전체 변경**은 바꿀 톤·색·광원과 영향받는 역할을 먼저 기록한다. 변경된 팔레트와 스타일은 새 버전으로 저장하고 견본 PNG를 다시 만든다. `art-direction.md`에는 현재 적용하는 버전과 변경 이유를 기록한다.
- 영향을 받는 매니페스트와 작업 명세를 새 버전으로 연결한다. 기존 승인 프레임을 새 기준으로 검수하고, 재보정이나 재생성이 필요한 결과만 갱신한다. 새 결과가 승인되면 기준 레퍼런스와 최종 PNG 경로를 바꾼다.

완성된 PNG는 이미지 뷰어나 픽셀 편집기에서 바로 열 수 있다. Unity에서 자동 분할이 필요한 경우 게임 프로젝트의 Unity 임포터 설정을 참고한다.
